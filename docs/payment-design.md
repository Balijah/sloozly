# Payment States & Idempotency Design

## Overview

Sloozly charges users a penalty when they snooze an alarm. Penalties are
processed as ACH debits via Stripe PaymentIntents. ACH debits are
asynchronous — they take 1–5 business days to settle — so the system
must track payments through multiple states and resolve them via webhooks.

## Penalty Lifecycle

```
Client sends snooze
        │
        ▼
  ┌──────────┐  unique (userId, occurrenceId, snoozeNumber)
  │  PENDING  │◄──── If duplicate → resume existing record
  └────┬─────┘
       │ create Stripe PaymentIntent with idempotency key
       ▼
  ┌────────────┐
  │ PROCESSING │  ACH debit submitted, awaiting settlement
  └────┬───────┘
       │
       ├── webhook: payment_intent.succeeded ──► COMPLETED
       │
       └── webhook: payment_intent.payment_failed ──► FAILED
```

## Idempotency

Each snooze event is identified by a durable **occurrence ID** — typically
`{alarmId}_{ISO-date}` — generated by the client and sent with every
`POST /api/penalties/trigger` request.

The tuple `(userId, occurrenceId, snoozeNumber)` is unique in the database.
The authenticated user is included in every lookup, so another user's occurrence
ID cannot expose or suppress a payment.

Stripe creation uses `sloozly_{penalty.id}`. The server creates an **unconfirmed**
intent, saves its ID, then confirms using `{key}_confirm` and the recorded mandate.
A retry resumes pending records; once an intent ID exists, it retrieves that intent
and only confirms if it is still awaiting confirmation. A crash before saving the
ID can leave an unused unconfirmed intent, but cannot debit the account. Network
failures keep the reservation rather than treating an unknown result as a decline.

The saved Plaid/Stripe `ba_` account is passed as `payment_method`, following
[Stripe's bank-account migration flow](https://docs.stripe.com/payments/ach-direct-debit/migrating-from-charges?integration-path=payment-intent).
It is not a Financial Connections account ID.

## Payment States

| Status | Meaning | How it transitions |
|--------|---------|-------------------|
| `PENDING` | Penalty record created, payment not yet submitted | → `PROCESSING` on Stripe call |
| `PROCESSING` | PaymentIntent created and confirmed; ACH in flight | → `COMPLETED` or `FAILED` via webhook |
| `COMPLETED` | ACH debit settled successfully | Terminal |
| `FAILED` | Payment rejected by bank or Stripe | Terminal |
| `REQUIRES_ACTION` | Stripe requires bank verification | → `PROCESSING` or `FAILED` |

**Key rule:** completion requires a succeeded Stripe status, from a webhook
or retrieval of the saved intent during recovery.

## Daily Cap

The server enforces a per-user daily cap (`PENALTY_DAILY_CAP_CENTS`,
default $25.00). Before creating a new penalty, it sums all
`PENDING + PROCESSING + COMPLETED + REQUIRES_ACTION` penalties for the
current calendar day in the user's saved timezone. The read and insertion run
inside one transaction holding a PostgreSQL row lock on the user. Concurrent
requests from different processes cannot each spend the same remaining cap.
If adding the flat penalty amount would exceed the cap, the penalty is
recorded with `amount: 0` and status `COMPLETED` (cap-hit marker) and
no Stripe call is made.

## Flat Penalty Amount

The penalty amount is a server-side configuration value
(`PENALTY_AMOUNT_CENTS`, default $5.00). The client does not send an
amount — the server determines it. This prevents client-side
manipulation and simplifies the first release.

## Webhook Processing

The `POST /api/webhooks/stripe` endpoint:

1. Verifies the Stripe signature using `STRIPE_WEBHOOK_SECRET`
2. Handles `payment_intent.succeeded` → marks penalty `COMPLETED`
3. Handles `payment_intent.payment_failed` → marks penalty `FAILED`
4. Ignores all other event types
5. Is idempotent: re-resolving an already-resolved penalty is a no-op

## Deletion Safety

- **Alarm deletion**: penalties are preserved (alarm FK set to NULL)
- **Account deletion**: blocked while payments are `PENDING`, `PROCESSING`, or `REQUIRES_ACTION`;
  user is soft-deleted (`deletedAt` set) and external resources (Stripe
  customer, Plaid item) are cleaned up before local records
- **Bank unlink**: calls Stripe `deleteSource` and Plaid `itemRemove`
  before removing the local record

## Mandate / Authorization

When linking a bank account, the client must send `mandateAccepted: true`.
The server records the acceptance timestamp, IP address, and user agent
on the `BankAccount` record. The Stripe PaymentIntent includes
`mandate_data.customer_acceptance` with this information.

## Sandbox / Test Mode

This system is designed for Stripe **test mode** and Plaid **sandbox**.
No real money is moved. All `sk_test_*` keys must be used.
